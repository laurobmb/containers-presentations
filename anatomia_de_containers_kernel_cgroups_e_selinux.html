Pilar 1 • Isolamento de Visão

Linux Namespaces: A Ilusão de uma Máquina Exclusiva

Criados via syscall clone() ou unshare(), particionam os recursos globais do sistema operacional.

Os 8 Namespaces do Kernel Linux /proc/[PID]/ns/

  • mnt (Mount) Sistemas de arquivos e pontos de montagem isolados.
  • pid (Process ID) Processo do container enxerga-se como PID 1.
  • net (Network) Tabela de rotas, veth pairs, iptables/nftables próprios.
  • user (User/Group) Mapeia UID 0 interno para UID 1000+ no host (Rootless).
  • ipc, uts, cgroup, time Memória compartilhada, Hostname, relógio e cgroups isolados.
terminal@rhel-host: ~ bash

# Inspecionando os namespaces de um container rodando no Podman:

$ podman run -d --name web docker.io/library/nginx

c982d61a5e4b...

$ sudo lsns -p $(podman inspect -f '{{.State.Pid}}' web)

NS TYPE NPROCS PID USER COMMAND net 1 12458 root nginx: master process mnt 1 12458 root nginx: master process pid 1 12458 root nginx: master process user 1 12458 root nginx: master process
💡 O host enxerga o PID real (12458); o container enxerga apenas o PID 1.
Pilar 2 • Gestão e Limitação de Recursos

cgroups v2: O Guardião Contra Starvation e OOM

Enquanto Namespaces isolam a visão, os Control Groups regulam e contam o consumo de hardware via pseudo-filesystem /sys/fs/cgroup/.

1. Memória (OOM Control) memory.max

Define limites rígidos (*hard limit*). Ao ultrapassar memory.max, o kernel aciona o Out-Of-Memory Killer (OOM) eliminando o processo filho ou o container antes de comprometer o host.

podman run -m 512m ...
↳ echo 536870912 > memory.max
2. CPU (CFS Quotas) cpu.max

Utiliza o Completely Fair Scheduler (CFS). Define quanto tempo em microssegundos de CPU o container pode utilizar dentro de uma janela de período (ex: 50000 100000 = 0.5 CPU).

podman run --cpus 1.5 ...
↳ echo "150000 100000" > cpu.max
3. PIDs & I/O Throttling pids.max

Impede Fork Bombs catastróficos restringindo a quantidade máxima de threads/processos criados, além de limitar taxas de leitura/escrita por disco em io.max.

podman run --pids-limit 100 ...
↳ echo 100 > pids.max
cgroups v2 no RHEL/Fedora Hierarquia unificada de processos, permitindo delegação sem privilégios para Rootless Containers com systemd --user.
Pilar 3 • Mandatory Access Control (MAC)

SELinux: A Fortaleza Contra Container Breakout

Por que permissões UNIX (DAC / `chmod 777` / root) são insuficientes e como o SELinux confina o processo no Kernel.

O Cenário de Risco (Sem SELinux / DAC puro)

Se um invasor explorar uma vulnerabilidade no container (ou no runtime) e conseguir escapar do Namespace ou montar o /etc do host, sendo UID 0 (root), ele terá acesso irrestrito de leitura e escrita ao kernel e a todos os arquivos do servidor.

⚠️ Discretionary Access Control (DAC): O dono do arquivo ou o Root decide quem acessa. Se o processo for root, o sistema cede.

A Proteção com SELinux (MAC)

O Kernel consulta a política de segurança do SELinux após o DAC. O processo do container roda sob o tipo restrito container_t. Ele só pode interagir com objetos explicitamente rotulados com tipos compatíveis (ex: container_file_t).

🛡️ Mandatory Access Control: Mesmo que o container seja root, ele recebe Permission Denied se tentar tocar em arquivos rotulados como shadow_t ou ssh_home_t.

SELinux Avançado • Multi-Category Security

MCS e o Segredo das Flags de Volume :z e :Z

Como o Podman impede que o Container A leia os dados do Container B mesmo ambos sendo do tipo container_t.

Anatomia de um Contexto SELinux Completo
system_u : system_r : container_t : s0:c142,c859

O Podman gera aleatoriamente um par de categorias MCS (c142,c859) para cada container. Containers com categorias diferentes não podem acessar os arquivos uns dos outros.

Flag :z (Compartilhado / Shared)

container_file_t (Sem MCS)

Instrui o Podman a reetiquetar o diretório do host para que múltiplos containers possam ler e escrever simultaneamente no mesmo volume montado.

podman run -v /app/data:/data:z docker.io/library/nginx

Flag :Z (Privado / Exclusive)

container_file_t:s0:c1,c2

Reetiqueta o diretório com a categoria MCS exata e exclusiva do container atual. Nenhum outro container no host terá permissão de ler este volume.

podman run -v /db/secret:/data:Z docker.io/library/postgres
Pilar 4 • Bloqueio de Syscalls e Privilégios

Seccomp Filters & Linux Capabilities

Como reduzir a superfície de ataque do Kernel através do descarte cirúrgico de chamadas de sistema.

Seccomp (Secure Computing)

BPF Filters

O Linux possui mais de 450 chamadas de sistema (syscalls). Um perfil Seccomp padrão no Podman bloqueia dezenas de syscalls perigosas que um container comum nunca deveria usar:

❌ reboot()
❌ kexec_load()
❌ init_module()
❌ swapon()

Linux Capabilities (posix)

Granular Root

O poder do root tradicional é fatiado em ~40 permissões. O Podman retira a grande maioria por padrão (como CAP_SYS_ADMIN, CAP_SYS_RAWIO):

# Descartando todas e concedendo apenas bind de portas:
podman run --cap-drop=ALL --cap-add=NET_BIND_SERVICE ...
⚡ Regra de Ouro da Segurança Enterprise: Nunca utilize --privileged em produção. A flag desativa o SELinux, o Seccomp, restaura todos os Caps e expõe os devices do host.
Arquitetura Podman • Sem Daemon & Sem Root

Podman Rootless: User Namespaces na Prática

Como você se torna o "Superusuário" dentro do container sem ter nenhum privilégio real no sistema operacional hospedeiro.

Mapeamento de UIDs (/etc/subuid)

Quando o usuário lucas (UID 1000) executa o Podman:

$ cat /etc/subuid
lucas:100000:65536
UID 0 no Container ➔ UID 1000 no Host (lucas)
UID 1 no Container ➔ UID 100000 no Host
UID 65535 no Container ➔ UID 165534 no Host

Vantagens do Modelo Fork/Exec do Podman

  • ✓ Sem Daemon Central: Não existe socket root exposto (`/var/run/docker.sock`). Se o Podman fechar, o container continua rodando através do conmon.
  • ✓ Auditd Transparente: O sistema de auditoria do Linux registra o UID real (`1000`) nas chamadas de sistema, ao invés de mascarar tudo sob um daemon de root.
  • ✓ Rede via Pasta / Slirp4netns: Stack de rede completa em User Space sem necessidade de pontes de rede privilegiadas.

Troubleshooting e Diagnóstico no RHEL

Como investigar negações de SELinux e gargalos de cgroups em ambientes corporativos.

1. Investigando SELinux (AVC Denials) /var/log/audit/audit.log

# Verificar se o SELinux está bloqueando seu container:

sudo ausearch -m AVC,USER_AVC -ts recent

# Obter a explicação legível e sugestão de correção:

sudo sealert -a /var/log/audit/audit.log

# Verificar contextos de arquivos montados:

ls -laZ /meu/diretorio/volume

2. Inspecionando cgroups v2 do Container /sys/fs/cgroup/

# Ver uso de recursos em tempo real estilo top:

podman stats

# Ver contadores de throttling de CPU no cgroupfs:

cat /sys/fs/cgroup/.../cpu.stat

# Checar se o container sofreu OOM (Out of Memory):

cat /sys/fs/cgroup/.../memory.events

💡 Se o seu container falha com "Permission denied" mesmo usando permissão 777 na pasta do host, em 99% dos casos é o SELinux bloqueando por ausência da flag :Z ou :z.

A Matriz Definitiva do Isolamento

O ecossistema Red Hat / Podman não reinventa a segurança: ele potencializa as capacidades nativas do Kernel Linux de forma transparente e declarativa.

Camada do Kernel Pergunta Fundamental Mecanismo Tecnológico Papel do Podman
Namespaces "O que eu posso ver?" PID, MNT, NET, USER, IPC, UTS Configura via unshare() / clone()
cgroups v2 "O quanto eu posso gastar?" CFS, OOM, memory.max, cpu.max Integração nativa com systemd slices
SELinux "O que eu posso acessar?" Type Enforcement (container_t) + MCS Gera categorias e rotula volumes (:z/:Z)
