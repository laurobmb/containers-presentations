Segurança em Kubernetes na Prática
Hardening, RBAC, Secrets e Observabilidade em Produção

Kubernetes não é seguro por padrão: RBAC permissivo, Secrets em texto base64, ausência de Network Policies e falta de auditoria são configurações-padrão que um administrador precisa corrigir explicitamente.

Por Que Proteger o Cluster? • Modelo de Ameaças (NSA/CISA)

As 3 Fontes de Comprometimento em Kubernetes

Segundo o guia oficial da NSA e CISA, praticamente todo incidente em clusters se origina em uma destas três fontes.

1. Supply Chain

Uma imagem, dependência ou peça de infraestrutura comprometida entra no cluster de forma "confiável". Inclui a camada de aplicação, o container runtime e a própria infraestrutura dos nós.

2. Malicious Threat Actor

Um atacante externo explora APIs expostas: o control plane (kube-apiserver), os worker nodes (kubelet/kube-proxy) ou a própria aplicação containerizada acessível pela internet.

3. Insider Threat

Administradores com kubectl exec, usuários com credenciais válidas ou até o próprio provedor de nuvem — todos com acesso legítimo que pode ser abusado.

⚠️ O ponto central desta aula: nada disso é hipotético — RBAC, Network Policies, criptografia de Secrets e auditoria são todos desabilitados ou permissivos por padrão em uma instalação vanilla do Kubernetes. Corrigir isso é responsabilidade explícita do administrador.

Fase 1 de 3 • Build

Build-Time Security: Blindando a Imagem Antes do Deploy

Retomando o podman build do Módulo 1 — agora com um usuário não-root e escaneamento de vulnerabilidades.

Containerfile Não-Root NSA Appendix A

FROM registry.access.redhat.com/ubi9/python-312

RUN useradd -u 1001 appuser

COPY --chown=appuser:appuser app.py .

USER appuser

CMD ["python", "app.py"]

Sem a linha USER appuser, a aplicação roda como root dentro do container por padrão — mesmo quando o processo não precisa de nenhum privilégio elevado.

terminal@rhel-host: ~/meu-app-python
🛠️ Boa prática: escaneie a imagem antes do push para o registry. Ferramentas como trivy, grype ou o scanner integrado do Quay identificam CVEs conhecidas em bibliotecas do sistema operacional e em dependências da aplicação (camada "Code" do slide anterior).
Fase 2 de 3 • Deploy

Pod Security: Non-Root, Read-Only FS e Pod Security Admission

Os mesmos pilares do Kernel do Módulo 2 (Namespaces, cgroups, SELinux, Seccomp) continuam por baixo — o que muda é quem garante que eles sejam usados corretamente.

# securityContext no nível do Pod e do container:

apiVersion: v1

kind: Pod

spec:

securityContext:

runAsNonRoot: true

seccompProfile: {type: RuntimeDefault}

containers:

- name: app

securityContext:

readOnlyRootFilesystem: true

allowPrivilegeEscalation: false

capabilities: {drop: ["ALL"]}

Pod Security Admission: 3 Níveis

Privileged — sem restrições. Reservado para componentes do próprio sistema (CNI, storage drivers).
Baseline — bloqueia os escapes mais conhecidos (hostPID, hostNetwork, privileged: true), mas permite root.
Restricted — exige non-root, seccomp e capabilities descartadas. É o padrão que o OpenShift aplica por Project (Módulo 3).
Fase 2 de 3 • Deploy

Network Policies: Zero Trust Também na Rede

Por padrão, todo Pod pode conversar com todo Pod — independente de Namespace.

Sem NetworkPolicy Allow All ➔ Allow All
➔ vs ➔
Com default-deny + allow explícito Deny All ➔ Só o permitido

# Política que nega TODO tráfego de entrada e saída em um namespace:

apiVersion: networking.k8s.io/v1

kind: NetworkPolicy

metadata: {name: default-deny-all, namespace: producao}

spec:

podSelector: {}

policyTypes: [Ingress, Egress]

✅ Checklist (NSA/CISA): use um plugin CNI que suporte a NetworkPolicy API → crie uma política default-deny por namespace → relaxe seletivamente com podSelector/namespaceSelector → combine com LimitRange/ResourceQuota para também limitar recursos.
Fase 2 de 3 • Deploy

Secrets: Por Padrão, NÃO São Criptografados

Um Kubernetes Secret é apenas texto em base64 — não é criptografia. Qualquer um com permissão de get secrets pode ler o valor original.

terminal@rhel-host: ~

Como Proteger de Verdade

1. RBAC restritivo — só quem realmente precisa deve ter o verbo get/list no recurso secrets.
2. Encryption at rest — configure --encryption-provider-config no kube-apiserver para criptografar Secrets dentro do etcd.
3. KMS externo — evita manter a chave de criptografia no disco local do control plane.
Fase 2 de 3 • Deploy

RBAC: Least Privilege na Prática

Role/ClusterRole definem o quê pode ser feito. RoleBinding/ClusterRoleBinding definem quem pode fazer.

kind: Role # só neste namespace

metadata: {name: pod-reader, namespace: producao}

rules:

- apiGroups: [""]

  resources: ["pods"]

  verbs: ["get","list","watch"]

---

kind: RoleBinding

subjects: [{kind: User, name: lucas}]

roleRef: {kind: Role, name: pod-reader}

terminal@rhel-host: ~
📌 Role = permissão em um namespace. ClusterRole = permissão em todo o cluster (ou reutilizável em vários namespaces via RoleBinding). Nunca use ClusterRoleBinding quando um RoleBinding resolveria — least privilege também vale para o escopo, não só para os verbos.
Fase 3 de 3 • Run

Audit Logging & Detecção de Ameaças

A auditoria nativa do Kubernetes vem desabilitada por padrão. Sem ela, um incidente não deixa rastro.

Nonenão registra nada
Metadatasó usuário, verbo, recurso — usar para Secrets
Request+ corpo da requisição
RequestResponse+ resposta completa — máximo detalhe

⚠️ Registrar Secrets em RequestResponse expõe o valor base64 no próprio log de auditoria.

terminal@rhel-host: ~
🔎 Sinais de alerta (NSA/CISA): requisições anônimas • picos súbitos de CPU/memória (cryptojacking) • Pods criados com privilégios de root • falhas repetidas de autorização • IP de origem de um Pod aparecendo como IP de criação de outro Pod.
Conectando com o Módulo 3

No OpenShift, Boa Parte Disso Já Vem Pronta

Tudo que vimos até aqui é sobre como corrigir as inseguranças padrão do Kubernetes vanilla. O OpenShift parte de uma postura diferente.

Controle Kubernetes Vanilla Red Hat OpenShift
Postura padrão de Pod Permite root; PSA "restricted" é opt-in SCC "restricted-v2" aplicada por padrão em cada Project
Isolamento SELinux Depende da distro do nó Categorias MCS únicas por Project (Módulo 2)
Auditoria Desabilitada, requer configuração manual Habilitada por padrão no control plane gerenciado
RBAC inicial Service account "default" com poucos privilégios, mas sem Projects/self-service Projects com RBAC + cotas de recurso prontos
💡 O OpenShift não inventa mecanismos novos — ele apenas assume, por padrão, as configurações mais seguras dos mesmos primitivos do Kubernetes que estudamos nesta aula.
Ecossistema Prático

Ferramentas que Todo Time Deveria Conhecer

Kubernetes não tem auditoria, scanning ou alerting completos nativamente — o ecossistema preenche essa lacuna.

CIS

kube-bench

Audita a configuração do cluster contra os benchmarks do CIS.

IMG

Trivy / Grype

Escaneiam imagens de container por CVEs conhecidas antes do deploy.

RT

Falco

Detecção de ameaças em runtime via eBPF/Seccomp — o "IDS" do container.

POL

OPA / Kyverno

Policy-as-code via admission controller: bloqueia manifests fora do padrão.

Observabilidade (a outra metade da segurança):

Prometheus + Grafana: métricas de CPU/memória/rede — uma baseline sólida ajuda a identificar desvios (ex: cryptojacking).
Service Mesh (ex: Istio/Linkerd): criptografia mTLS automática entre serviços e visibilidade completa do tráfego interno.
