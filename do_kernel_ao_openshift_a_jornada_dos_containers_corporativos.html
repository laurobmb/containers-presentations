Passo 1 • O Elo Local

Podman: O Laboratório de Bolso do Kubernetes

Ao contrário de outros runtimes, o Podman foi construído pensando na unidade fundamental do Kubernetes: o Pod.

O Conceito de "Pod" no Podman Infra Container

Um Pod é um grupo de containers que compartilham os mesmos Network, IPC e UTS Namespaces. No Podman, assim como no Kubernetes, isso é viabilizado por um Infra Container (pause container) que segura os namespaces ativos enquanto os containers de aplicação sobem e descem.

terminal@rhel-host: ~

Da Máquina Local ao Manifesto K8s 100% Declarativo

O Podman possui integração bidirecional nativa com manifestos do Kubernetes através dos comandos kube generate e kube play.

terminal@rhel-host: ~

✓ O desenvolvedor testa o pod exatamente como ele executará no cluster de produção.

Passo 2 • Orquestração Multihost

Por Que o Podman Sozinho Não Basta em Produção?

O Podman governa uma única máquina Linux. O Kubernetes orquestra milhares de máquinas sob um estado desejado.

1. Agendamento Inteligente (Scheduler)

Em qual nó rodar? O Kubernetes avalia afinidades, taints, tolerations e recursos de CPU/Memória disponíveis em tempo real para alocar Pods no melhor host físico ou virtual.

2. Self-Healing & Resiliência

Se um nó falha ou sofre pane elétrica, os controladores do Kubernetes detectam a perda e recriam os Pods instantaneamente em outros nós operacionais da infraestrutura.

3. Rede Overlay & Service Discovery

Atribuição automática de IPs dinâmicos, balanceamento de carga interno via Services e malhas de roteamento que interconectam centenas de nós em uma rede plana.

Passo 3 • Anatomia do Worker Node

Como o Kubernetes Fala com o Kernel: CRI-O e crun

Conforme a documentação oficial do OpenShift 4.22, o CRI-O é o motor nativo e o crun é o runtime OCI padrão (runC está obsoleto).

O Caminho da Execução no Node

  1. 1 Kubelet: Agente principal do nó que recebe o pod spec da API do cluster.
  2. 2 gRPC / CRI API: O Kubelet invoca o crio.service via socket UNIX.
  3. 3 CRI-O Container Engine: Gerencia imagens, monta volumes e aciona o runtime OCI.
  4. 4 crun (OCI Runtime em C): Substitui runC com menor footprint de memória e suporte ultrarrápido a cgroups v2.
A Reutilização dos Mesmos Pilares do Kernel:

O nó do Kubernetes não faz mágica: quando o crun inicia o pod solicitado pelo Kubelet, ele aplica exatamente os mesmos pilares que vimos no Podman:

cgroups v2: kubepods.slice / burstable / guaranteed
SELinux: system_u:system_r:container_t:s0:c...
Namespaces: mnt, pid, net, ipc, uts separados
🔍 Insight de Engenharia: Podman e OpenShift utilizam a mesma biblioteca e ecossistema subjacente (containers/storage, containers/image e crun). O que você aprendeu com Podman é o que roda em cada worker do cluster!

A Base Imutável • OCP 4.22

RHCOS: O Sistema Operacional Gerenciado Como Container

No OpenShift 4, o sistema operacional hospedeiro não é tratado como uma entidade separada: ele é um componente do próprio cluster.

Red Hat Enterprise Linux CoreOS (RHCOS)

Baseado no RHEL (na versão 4.22, RHCOS baseia-se no RHEL 9.8), é um sistema operacional imutável desenhado especificamente para rodar containers.

  • Ignition: Provisionamento no primeiro boot (particionamento, usuários e configs).
  • rpm-ostree: Atualizações atômicas transacionais em árvore de arquivos completa.
  • Bootable OCI Images: Na v4.22, o SO é entregue e versionado como imagem de container.

Machine Config Operator (MCO)

O MCO garante que os nós nunca sofram "configuration drift" (divergência de configuração manual por SSH):

1. Administrador cria um manifesto MachineConfig

2. MCO renderiza uma nova versão para o pool (MCP)

3. O Machine Config Daemon (MCD) aplica a mudança no host

4. Drena o nó, atualiza o kernel/SELinux de forma atômica e reinicia

⚡ Zero intervenção manual em servidores: infraestrutura como código real no nível do kernel.

O Padrão Arquitetural • OCP 4.22

Operators: Conhecimento Humano Codificado em Software

No OpenShift, os Operators não são apenas utilitários: eles formam 100% da base do Control Plane e do ecossistema de aplicações.

Operações Day 1 vs. Day 2 Automatizadas

Tradicionalmente, administradores usavam scripts bash ou playbooks externos para instalar bancos de dados, configurar backups e gerenciar failover. Um Operator encapsula esse conhecimento dentro de um loop de controle nativo do Kubernetes.

Day 1 Deploy automático, provisionamento de discos e certificados TLS.
Day 2 Backup periódico, auto-scaling, failover e patch upgrades sem downtime.

Evolução: OLM v1 no OCP 4.22

GA Feature

A documentação do OCP 4.22 consolida o OLM v1 como Generally Available, introduzindo a API ClusterExtension:

  • ✓ GitOps Friendly: Gerenciamento declarativo simplificado de extensões via repositório Git.
  • ✓ Menor Complexidade: Resolução de dependências mais robusta e menor impacto no cluster.
OperatorHub & Red Hat Quay: Catálogo corporativo integrado com centenas de Operators certificados (Postgres, Kafka, OpenShift GitOps, OpenShift Pipelines, OpenShift Virtualization).
Governança & Segurança • OCP 4.22

Multitenancy Corporativo: Namespaces vs. Projects

Como o OpenShift isola múltiplos times e workloads com base nos pilares de segurança do Linux.

1. Projects

No Kubernetes puro, o Namespace é um conceito técnico plano. No OpenShift, um Project é um namespace envelopado com RBAC, cotas de recursos (ResourceQuota), limites e permissões de autoatendimento para desenvolvedores.

2. SELinux MCS Automático

Lembram das categorias MCS do Podman? O OpenShift atribui um par de categorias MCS único para cada Project. Mesmo se um pod de um tenant diferente for comprometido, o SELinux no Kernel impede que ele acerte os volumes de outro projeto.

3. Security Context Constraints

As SCCs controlam as ações que um pod pode executar no cluster (como rodar como root, acessar host ports ou montar host paths). Por padrão, nenhum container roda como root no OpenShift sem concessão explícita.

🔒 Novidade no OpenShift 4.22: Conforme as release notes, componentes de plataforma e Operators agora utilizam Service Accounts estritamente dedicadas em vez da default, isolando identidades de sistema das cargas de trabalho de usuários.

A Matriz Evolutiva: Do Kernel ao OpenShift

Como cada conceito se transforma ao longo da pilha tecnológica:

Camada Conceitual 1. Kernel & Podman 2. Kubernetes Padrão 3. Red Hat OpenShift 4.22

Conclusão para os Alunos:

Não há ruptura entre o que acontece no terminal com Podman e o que acontece em um cluster OpenShift de 500 nós. O OpenShift é a orquestração do Kubernetes elevada a uma plataforma empresarial completa, ancorada firmemente nos mesmos pilares de segurança e controle de recursos do Kernel Linux.
