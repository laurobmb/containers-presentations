Por que Containers?

O Fim do "Na Minha Máquina Funciona"

Como a indústria migrou do acoplamento direto no S.O. para unidades padronizadas de software.

1. Máquinas Virtuais (VMs)

Pesado & Lento
  • ✖ S.O. Convidado Completo: Cada VM roda sua própria instância inteira de sistema operacional (Kernel + Binários + Libs).
  • ✖ Alto Consumo: Gigabytes de memória RAM e disco alocados rigidamente via Hypervisor antes mesmo do app iniciar.
  • ✖ Boot Demorado: Minutos para inicializar uma aplicação simples.

2. Linux Containers

Leve & Eficiente
  • ✔ Kernel Compartilhado: O container é apenas um processo isolado executando diretamente sobre o Kernel do Host.
  • ✔ Consumo Mínimo: Carrega apenas a aplicação e suas dependências diretas (Megabytes em vez de Gigabytes).
  • ✔ Boot Sub-segundo: Inicia na mesma velocidade com que o Linux dispara um novo processo.
📦 Analogia Prática: Se a VM é uma casa inteira construída para cada morador, o Container é um apartamento individual que compartilha a fundação, encanamento e rede elétrica do mesmo prédio.
Padronização Global

Open Container Initiative (OCI)

Garantindo que imagens geradas em qualquer ferramenta rodem em qualquer plataforma interoperável.

1. OCI Image Spec

Especificação de Imagem

Define o formato do arquivo tarball, camadas imutáveis (layers), manifiestos JSON e metadados. Qualquer imagem criada via Podman, Buildah ou Docker segue esta norma.

2. OCI Runtime Spec

Especificação de Runtime

Define como descompactar a imagem e invocar o Kernel Linux (usando executáveis leves de baixo nível como crun ou runc) para criar o container.

3. Distribution Spec

Especificação de Registry

Padroniza a API HTTP para fazer push/pull de imagens em repositórios remotos como Quay.io, Docker Hub ou Red Hat Ecosystem Catalog.

💡 Por que isso importa para você? Você pode construir uma imagem no seu notebook com Podman, testar localmente, subir para um repositório Quay.io e rodar no Kubernetes / OpenShift em produção sem precisar modificar uma única linha de código.
Evolução de Arquitetura

Por que o Podman Nasceu? O Fim do Monolito Daemon

A mudança de paradigma: saindo do modelo Cliente/Servidor centralizado para a execução direta.

O Modelo Tradicional (Docker) dockerd Daemon

A CLI se comunica através de um Socket com um serviço central rodando como Root em segundo plano.

CLI ➔ /var/run/docker.sock ➔ Daemon Root ➔ Container
  • Single Point of Failure: Se o daemon reiniciar ou travar, todos os containers caem.
  • Vulnerabilidade de Segurança: Acesso ao socket equivale a privilégios root totais no servidor.

O Modelo Podman (Fork / Exec) Daemonless

O comando instanciatamente cria o processo diretamente como filho da sua sessão de usuário.

Podman CLI ➔ crun (OCI Runtime) ➔ Processo do Container
  • Sem Daemon: Se a CLI fechar, o container continua rodando de forma independente.
  • Rootless Por Padrão: Usuários comuns lançam containers sem privilégios de administrador.
Transição amigável de comandos: alias docker=podman
Características Fundamentais

Os Três Pilares do Podman

Segurança, arquitetura limpa e prontidão para a nuvem.

1

Daemonless

Elimina o serviço em segundo plano. Economiza memória em repouso e melhora a integração com sistemas de gerenciamento como o systemd e ferramentas de auditoria Linux (auditd).

2

Rootless First

Projetado do zero para rodar sem permissões de root. Utiliza User Namespaces para mapear seu usuário local no host para o usuário root dentro do container, isolando completamente o sistema.

3

Pods Nativo

Suporta o conceito de Pods do Kubernetes diretamente no seu terminal local. Agrupe múltiplos containers que compartilham endereço IP, portas e volumes antes de enviar para o cluster.

Hands-On • Comandos Essenciais

Ciclo de Vida do Container com Podman CLI

Comandos idênticos ao padrão da indústria para gerenciar seus workloads.

// 1. Baixar e Executar um Servidor Web em Background

$ podman run -it --rm --name meu-web -p 8080:80 docker.io/library/nginx

// 2. Listar containers em execução

$ podman ps

CONTAINER ID IMAGE COMMAND STATUS PORTS a81f32c91b8a docker.io/library/n... nginx... Up 5 seconds 0.0.0.0:8080->80/tcp
// 3. Inspecionar logs da aplicação

$ podman logs -f meu-web

// 4. Entrar dentro do container em modo interativo

$ podman exec -it meu-web bash

// 5. Parar e remover o container

$ podman stop meu-web && podman rm meu-web

💡 Boa prática: Diferente do Docker, o Podman pode pedir para você escolher o registro quando o nome da imagem é "curto" (ex: nginx). Prefira sempre nomes totalmente qualificados, como docker.io/library/nginx, para evitar ambiguidade e prompts inesperados em scripts.
Recurso Exclusivo do Podman

Criando e Gerenciando "Pods" Localmente

Como agrupar containers que trabalham juntas (ex: Aplicação Web + Banco de Dados).

O que acontece dentro de um Pod?

Um Pod contém um Infra Container (Pause) que reserva a rede e os recursos. Todos os outros containers adicionados ao mesmo Pod conversam entre si via localhost.

POD: meu-app-pod (Porta 8080)
├─ Infra Container (Rede / IP isolado)
├─ Container 1: App Python (Porta 5000)
└─ Container 2: NGINX Reverse Proxy (Porta 80)
// Passo A: Criar o Pod expondo a porta para o Host

$ podman pod create --name meu-pod -p 8080:80

// Passo B: Adicionar container de aplicação no Pod (imagem construída localmente)

$ podman run -it --rm --pod meu-pod --name app localhost/meu-app-python

// Passo C: Adicionar NGINX no MESMO Pod

$ podman run -it --rm --pod meu-pod --name proxy docker.io/library/nginx

Comparando arquitetura, segurança e facilidade operacional para times de TI enterprise.

Recurso Docker Traditional Red Hat Podman

Do Terminal para o Kubernetes

Podman: A Rampa de Acesso para a Nuvem

Como criar manifests Kubernetes sem precisar escrever arquivos YAML manualmente do zero.

1. Exportar para Kubernetes YAML

Crie seu container ou Pod localmente com Podman e exporte a especificação pronta para o Kubernetes:

$ podman kube generate meu-pod > pod.yaml
2. Executar YAMLs do Kubernetes Localmente

Recebeu um manifesto de um desenvolvedor? Rode direto no seu computador usando o Podman:

$ podman kube play pod.yaml
ℹ️ Nota de versão: Antes do Podman 4.2, esses comandos eram escritos como podman generate kube e podman play kube. Essa forma antiga ainda funciona como alias, mas podman kube generate / podman kube play é a sintaxe atual recomendada.
